# 第 6 期：验证二级——自主循环的"完成判据"（/goal）

> 时长 5 分钟 | 交付物：可验证完成判据写作清单 + /goal 好坏判据对照示例 | 前置：第 1 期（谎报完成）、第 5 期（Stop hook 验收）

## 逐字稿

### 0:00–0:30 导入：循环里的谎报完成

【口播】
先看一个场景。晚上十点，你给 agent 挂上循环："把这个模块重构完，测试全绿再停。"然后你去睡了。早上七点打开终端——循环第一轮就结束了，agent 报告"重构完成"。你一跑测试，红的。第五期讲过，单次任务的"完成"可以用 Stop hook 收归 harness。但只要循环一挂上、任务一拉长，"完成"的定义问题会换一层皮回来。这一期就讲：自主循环的完成判据怎么写。

【画面】
录屏：终端里循环日志显示"Iteration 1: goal achieved"，旁边 `npm test` 输出一片红。字幕卡：第五期解决的是单次，这期解决的是循环。

### 0:30–0:50 三代考古：技巧在迭代，模式在沉淀

【口播】
先考个古。最早是 Geoffrey Huntley 的 Ralph loop：一行 bash 循环，每轮新开上下文喂同一个 prompt；Anthropic 收编成官方插件，今年各家内置——Claude Code 有 /goal，Codex 有 Goals。技巧在迭代，模式在沉淀：第一期那个半衰期判据，这期现身说法。

【画面】
三段时间线图示：bash while 循环代码片段 → ralph-wiggum 插件目录截图 → /goal 命令面板。字幕：技巧在迭代，模式在沉淀。

### 0:50–1:20 机制揭秘：/goal 是什么

【口播】
/goal 不是黑魔法。官方文档给它的定义打在屏幕上，就一句话——它就是你第五期手写那个 Stop hook 的官方封装。机制完全一样：agent 每次想停，harness 拦一下，拿你的目标对照当前状态，判定没达成就让它继续。区别只在判定方式：第五期你写 shell 脚本，这里换成了模型评估。所以判据写得好不好，直接决定循环靠不靠谱。

【画面】
录屏：输入 /goal，展示它注册的 Stop hook 配置；并排第五期的手写 settings.json。字幕卡（静止 3 秒，观众自读）：官方文档原话——"session 级 prompt-based Stop hook 的快捷方式"；Codex Goals 同理，完成条件 = 配置面。

### 1:20–2:05 正菜一：判据的两个经典死法

【口播】
正菜。判据有两个经典死法。第一个，写太松。"完成用户管理模块"——这种判据等于把验收权又交回 agent 自己。注意它的失效形态不一定是你想的"秒退"：我们实测"让这个项目看起来完善了"，它跑了 25 轮、六分半钟才停——重构、补测试、加 LICENSE，全都没人让它做。判据松，烧的不是误判，是蔓延：目标没有边界，每一轮都在镀金。第二个死法，写太死：把你能想到的条件全堆进一条判据——屏幕上这份就是典型。听着严谨，实际是写了一个永远停不下来的循环：我们实测"证明这个项目没有任何 bug，有百分之百把握才算完成"，七分钟烧掉 27 轮还在跑，只能强杀。屏幕上就是这两段实录 transcript，轮数和耗时都在画面上。

【画面】
策展 transcript 分屏对比（2026-08-06 一落实测样本，`spike/captures/ep06-loose/ep06-impossible.stream.jsonl`，字幕如实标注运行条件）：左侧松判据 25 轮 / 6.5 分钟 / $0.41——镀金蔓延（重构、补测试、加 LICENSE 全是自发）；右侧死判据 7 分钟 27 轮未停、超时强杀。无实拍翻车。分屏前弹字幕卡（观众自读）：死判据清单示例——测试全过 + 覆盖率 ≥90 + lint 零警告 + 文档同步更新。

### 2:05–2:55 正菜二：可验证的判据长什么样

【口播】
中间的活路只有一条：判据必须指向外部信号——harness 能自己执行、自己读取的事实，不靠 agent 的自我感觉。写法的分水岭就一句话：把"做到什么程度"改写成"什么命令跑出什么结果"。"完成用户管理模块"改写成：`npm test` 全绿，且 migrations 目录里存在编号大于 0042 的迁移文件。前者是愿望，后者是判据。可验证还有第二层意思——验证逻辑必须独立于实现。第五期讲过，它会删测试让验证通过；放进循环里，这个博弈会重复一百次，目标本身也会在长循环里悄悄漂移。指标一旦变成目标，它就不再是好指标——Goodhart 定律，记住这个名字，第八期还会见到它。

【画面】
字幕卡：外部信号举例——测试通过 / build 成功 / 文件存在且符合 schema（完整对照表在交付物）。愿望 vs 判据改写对照。重点句加粗："把'做到什么程度'改写成'什么命令跑出什么结果'"。段尾字幕卡：goal drift——判据每轮重新注入，别靠 agent 记住。

### 2:55–3:25 失效模式：质量回退、预算

【口播】
判据对了，循环还有两个坎。第一，无人值守质量回退：测试全绿和代码变好是两回事，循环保证前者，保证不了后者——屏幕上这篇警告很直接：长期无人值守的循环，产出质量可能比你自己写的还差。这是你上不上循环结构的关键输入。第二，预算：循环必须带硬停止，最大轮次、成本上限，都设。

【画面】
两张字幕卡依次出现：质量回退（Ronacher 博客标题截图）/ 硬停止（max iterations + cost cap）。

### 3:25–3:55 选型：/goal vs /loop vs 交接三件套

【口播】
选型很简单。目标驱动用 /goal；定时轮询用 /loop；超出模型能力边界的超长任务，回手动交接三件套。怎么判断？看 METR：agent 能可靠完成的任务长度，近几年一直在翻倍，数字在屏幕上。但注意，百分之五十可靠性的边界和百分之八十的差着好几倍，而且他们任务集偏干净、可自动评分，你手头的活更糙。保守做法：按百分之八十那档判断。

【画面】
决策树图示：目标驱动 → /goal；定时轮询 → /loop（时间驱动的内置 skill）；超出 horizon → 交接三件套（字幕标注：JSON 任务清单 + 进度文件 + git 历史，文件即接口）。METR 翻倍曲线截图，字幕标注（观众自读）：翻倍时间约 3–4 个多月 / 50% vs 80% 可靠性双数字 / 任务集偏干净、可自动评分。

### 3:55–4:20 半衰期判据

【口播】
老问题：模型再强一倍，这期内容还成立吗？/goal 这个形态本身大概率会变——它自己就是 Ralph 的转世，明年可能换个名字、换个封装。但有一条不会变：自主循环的可靠性，等于完成判据的可验证性。模型越强，越容易把"我觉得做完了"当成做完了；而外部信号不随模型代际改变。写判据这个能力，半衰期无限。

【画面】
字幕卡：/goal 形态会变；可靠性 = 完成判据的可验证性，不变。

## Demo 详细步骤

**主 demo（实录，0:50–1:20 机制揭秘段）**

1. 准备一个含已知失败测试的示例 repo（模板仓库 `ep06/demo/`：`npm test` 初始为红，`migrations/` 目录为空）。
2. 终端启动 Claude Code（v2.1.139+），输入 `/goal`。
3. 设定判据："`npm test` 全部通过，且 `migrations/` 中存在编号大于 0042 的迁移文件"。
4. 展示 /goal 注册的 Stop hook 配置（session 级），与第五期手写 settings.json 并排。
5. 预期结果：agent 每轮尝试结束时被 Stop 判定拦回，直到测试真绿、迁移文件真存在才停。

**B 方案（录不到时）**：/goal 语法处于快速迭代期（二审遗留事项：开拍当月以官方文档复核）。若现场行为异常，改用文档截图 + 旁白讲机制，演示段换成模板仓库里预录的 transcript 逐行讲解。

**翻车段（1:20–2:05）不实拍**：松判据"第一轮宣布达成"是概率性失败，按制作纪律用策展 transcript，画面必须标注"选自十余次运行的典型样本"。死判据"烧穿预算"同理，展示循环日志的时间戳和 token 消耗即可，无需现场烧三小时。

**录不到翻车样本时的兜底**：文字板复述两个失效模式 + 判据对照表，跳过 transcript 画面。

## 交付物文件内容

模板仓库 `ep06/verifiable-goal-checklist.md`：

```markdown
# 可验证完成判据写作清单

写 /goal（或任何自主循环的停止条件）之前，逐条过：

1. **每个判据都能映射到一条命令**：说出"什么命令、什么退出码、什么输出"算达成。
   写不出命令的判据 = 新的谎报入口。
2. **信号来自外部世界**：测试通过、build 成功、文件存在且符合 schema、接口返回 200。
   不来自 agent 的自我评估（"代码看起来完整"不算）。
3. **验证逻辑独立于实现**：测试文件受保护（第 3 期的 PreToolUse hook 换个路径即可），
   agent 不能通过删测试、改断言来"达成"判据。
4. **判据每轮重新注入**：不靠 agent 记住目标，防 goal drift。
5. **硬停止必须存在**：最大轮次 + 成本上限，两个都设。循环没有免费的"再试一轮"。
6. **先问任务在不在 horizon 内**：按 80% 可靠性那档估；超出的任务用交接三件套，
   不上循环结构。

## 坏判据 vs 好判据

| 坏（愿望） | 好（判据） |
|---|---|
| 完成用户管理模块 | `npm test` 全绿，且 `migrations/` 存在编号 >0042 的迁移文件 |
| 把性能优化好 | `npm run bench` 输出中 p95 延迟 < 200ms |
| 修复所有 bug | 指定 issue 列表中每条的复现脚本退出码为 0 |
| 重构这个目录 | `npm run build` 成功 + 公共 API 类型检查（`tsc --noEmit`）零错误 |
| 全部测试通过、覆盖率 ≥90%、lint 零警告、文档同步更新 | （拆成多个循环，每个循环一个可验证目标）——写太死 = 永远停不下来 |
```

## 作业（≤10 分钟，带外部判据）

1. 在你自己的仓库里挑一个 10 分钟内能完成的小任务（修一个已知失败的测试即可）。
2. 按清单把目标改写成可验证判据，用 `/goal` 挂循环跑完。
3. **外部判据**（不看 agent 的报告，跑检查脚本）：

```bash
# 模板仓库 ep06/check-goal-run.sh：验证循环里测试命令真实执行过
# 1) 找到本项目最近一次 session 的 transcript
# 2) 断言其中至少出现一次包含测试命令的 Bash 工具调用
# 3) 你本人手动重跑测试套件，必须全绿
bash check-goal-run.sh "npm test" && npm test
```

三项全过才算完成：脚本确认测试命令在循环中被真实执行 ≥1 次；你手动重跑测试为绿；判据符合清单第 1、2、5 条（能映射到命令 / 外部信号 / 带硬停止）。
