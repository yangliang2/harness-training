【口播】
这段是实拍。我让 agent 给一个折扣函数写实现加测试，交付了：实现，加一版测试套件，全部通过。绿灯，看着很踏实。然后我做了件事：打开实现，把大于号改成大于等于——一个边界 bug——再跑一遍测试。还是全绿。整套测试，没有一个发现函数的核心逻辑已经错了。测试是通过的，测试也是没用的。今天讲的就是这件事：谁来测试测试。

### 0:30–1:15 核心翻转：一门几百年的老学科

【口播】
先给本期一个定性：接下来"三层对抗"的讲法，是本课提出的分析视角——组织理论和古德哈特定律的应用，不是有现成文献背书的定论。但反过来这件事有几百年证据：人类组织设计，就是面向"智能但不可靠个体"的 harness engineering。回头看前七期，每个机制都有一个活了上百年的名字——五条连线打在屏幕上，暂停自己看。我们不是在发明新学科，是给一门老学科换了新的执行体。

【画面】
图示：左列"前七期机制"，右列"组织学名字"，逐条连线动画，连完整体定格 3 秒供自读：CLAUDE.md→成文制度 / 权限和沙箱→最小授权 / 交接三件套→轮班交接 / Stop hook 验收→职责分离 / evals→独立审计。

### 1:15–1:55 三层对抗架构图

【口播】
把组织设计搬到 harness 上，就是这张图。一共三层，今天只讲第二层。第一层，开发对测试——生成和评估分离，第五期讲过，不重复；Anthropic 官方博文的原话打在角标，一句话：独立的怀疑者，远比自我批评可行。第二层，本期正菜：如果第一层合谋呢？测试和实现出自同一个 agent，可能共享同一套误解——开场那段就是。解法是审计，名字很直白：变异测试——往代码里植入 bug，看测试套件抓不抓得到。测试测试的人。第三层，局部对全局：每个 subagent 的 prompt 就是它的 KPI，局部最优加总不等于全局最优——第六期埋的古德哈特引线，今天烧到头。

【画面】
三层架构图（开发⇄测试 / 审计 / 局部⇄全局），讲到哪层高亮哪层。角标字幕："分析框架为本课提出"。第一层亮出时弹原话卡（观众自读，不占口播）：Anthropic《Harness design for long-running application development》——"把一个独立 evaluator 调成怀疑论者，远比让 generator 自我批评可行"。

### 1:55–3:05 演示：变异测试实拍

【口播】
实拍，一次过。左边是 agent 写的折扣函数，右边是它的测试套件，全绿。装 mutmut——Python 生态的变异测试工具，JS 的对应物和安装命令打在屏幕上，都是成熟工具。跑起来。它做的事很机械：遍历源码，每次只做一个微小改动，比如把大于改成大于等于——完整的换法清单在屏幕上。然后，每个变种跑一遍测试套件。变种被测试杀死，说明测试真在守这行代码；变种存活，说明这里有洞，测试没看着。跑完：一批变种存活。点开第一个——正是我刚才手工植入的那一类，会员边界。一版全绿的测试，一排盲区。注意，这不是模型笨——这一代的自我验证明明在增强；这是结构问题：测试和实现出自同一支笔，自己判自己必然放水。激励问题，不是能力问题。

【画面】
录屏：终端 `mutmut run` 进度（等待段打"已剪辑"字幕）→ `mutmut results` 存活列表 → `mutmut show` 展示一个 survived mutant 的 diff。安装段弹字幕卡（观众自读）：JS/TS 对应 Stryker（`npx stryker run`）；常见换法清单：大于↔大于等于、加一↔减一、True↔False。具体变种数以实拍为准，字幕如实标注。

### 3:05–3:45 原理：审计为什么必须独立于被审计者

【口播】
两个补充。第一，单 agent 放水、盲测 tester 写出纸老虎测试，这两段概率性翻车我不赌现场复现，用策展 transcript——选自多次运行的典型样本；单 agent 那段就是第一期谎报完成的同款素材，"盲测"是什么，下一段马上讲。第二，变异测试给你的是一个数字：mutation score，被杀变种的占比。它不依赖任何人、任何模型的自我报告——这是它能当审计用的根本原因。它测的不是代码质量，是测试套件的忠诚度。

【画面】
策展 transcript 截图（打水印"选自 N 次运行的典型样本"）→ mutation score 数字放大卡。

### 3:45–4:15 动作：subagent 双岗位结构

【口播】
落地动作：把"写的人"和"测的人"拆成两个 subagent。模板仓库里是两个成品：implementer 只管实现；blind-reviewer 只拿需求规格，不看实现代码，盲写测试，再配 mutmut 做第二层审计。说实话：这个"盲"目前靠 prompt 约定维持，是概率机制不是焊死的——所以变异测试这道确定性审计不是选修，是这个结构的兜底。职责分离从来不是靠说一句"请你严格一点"。仓库有三十秒导览，配置自己拿。

【画面】

### 4:15–4:40 判据：三个没有答案的问题

【口播】
收尾留三个问题，都没有答案。对抗层数有没有尽头？谁来审计审计者——人类组织的诚实回答是：看你愿意付多少对抗税，为对抗结构持续花的成本。全局目标能不能被编码？你的公司和 alignment 研究，共同未解。模型再强，对抗结构还需要吗？我的判断：谎报、跑偏这类能力型失效会缓解；博弈信号、钻规则空子这类激励型失效，随能力升值——但对抗层的具体形态同样会过期。这是本课的边界条件，不是永恒定律。

## Demo 详细步骤

### 演示 A：纸老虎实录（开场翻车，确定性）

1. 准备 demo 目录：`discount(price, is_member)` 之类的边界敏感函数（会员门槛、满减阶梯），让 agent 一次性产出实现 + pytest 测试套件。
2. 跑 `pytest`，确认全绿。
3. 手动把实现里 `>` 改成 `>=`（或 `+ 1` 改 `- 1`），重跑 `pytest`。
4. 预期：仍然全绿。**此步骤确定性成立的前提是测试本身漏了边界**——开拍前先让 agent 生成一次，人工植入验证必现；若 agent 某次写出的测试恰好覆盖边界，换一个边界更多的函数重生成，直到拿到"全绿但有洞"的样本。这不是造假，是策展，口播不声称"agent 必然漏边界"。
5. B 方案：实拍环境出问题时，用预先录好的同流程录屏，加"已剪辑"字幕。

### 演示 B：变异测试实拍（正菜，确定性）

1. 沿用演示 A 的原始（未植入 bug）代码与测试。
2. 隔离环境安装：`python -m venv .venv && pip install mutmut`（不污染系统环境）。
3. `mutmut run`（首次全量跑，等待段剪辑）；`mutmut results` 查看 killed/survived 统计；`mutmut show <id>` 展示一个 survived mutant 的 diff。
4. 预期：至少存在 survived mutant（演示 A 已证明测试有洞，mutmut 会系统性地把同类的洞都翻出来）。**已实测（`spike/NOTES.md`）**：报错文案类变异稳定存活，存活清单不为零是有兜底的；但当前模型对折扣函数这种"小函数+规约明确"的测试已能杀死全部逻辑变异——若实拍现场的 agent 套件把逻辑变异杀光，存活的报错文案变种直接用来演示"分诊"（补测试 or 论证等价），不强行编洞。
5. B 方案：mutmut 在目标技术栈表现不佳时换 Stryker（`npx stryker run`，JS/TS 项目）；两者都出问题则用预录 transcript（手写弱套件版本已在 `spike/pit-mutation-demo` 验证：洞 100% 可检出，可作预录素材源）。**大纲二审遗留事项已闭环：2026-08-06 实测 mutmut/PIT 对 agent 生成套件的检出表现，见 `spike/NOTES.md`。**
6. 口播中的变种数量（"杀死多少、存活多少"）一律以实拍实际数字为准，脚本不写死。

### 演示 C：v1/v2 策展 transcript（不实拍）

- v1（单 agent 放水）：直接复用第一期开场素材（"诚实的未完成"：agent 宣布完成时 6 个测试红灯，`spike/captures/ep05-stop-hook.stream.jsonl` 前段；2026-08-07 与第一期最终版本对齐——不再用"伪造测试通过"形态），打水印"实拍实录"（本节为策展呈现，不写"非策展"）。
- v2（盲测 tester 写出纸老虎测试）：✅ 2026-08-07 第三轮采到（`spike/ep08-messy`，订阅计费引擎规格：三档计划×用量×促销交互）。盲测 22 条全绿，mutmut 审计 5 个存活：4 个等价变种（`seats<=1` 恒等、`overage>=0` 加零、报错文案×2——天然"分诊"教学素材）+ **1 个真实逻辑洞**：超量费 `> 0` 变异为 `> 1` 存活——小数超量（0<overage≤1 GB）计费没有任何测试覆盖。策展这条 transcript 出镜："22 条全绿，变异审计抓到一个真洞和四个假阳性，假阳性也要人分诊——这就是对抗税"。前两轮简单/中等规格（阶梯电价、图书馆逾期费）存活全为等价变种，如实记录：这代模型盲写边界测试已相当扎实，纸老虎需要规格足够 messy 才压得住。

## 交付物文件内容

模板仓库期 8 目录：`ep08-subagent-org/`，含以下两个文件 + 本 README。

`.claude/agents/implementer.md`：

```markdown
---
name: implementer
description: 按需求规格实现代码。不写测试——测试由 blind-reviewer 独立编写。
tools: Read, Edit, Write, Bash, Grep, Glob
---

你是实现者。你的唯一职责是按需求规格写出正确、简洁的实现。

约束：
- 不要编写或修改任何测试文件。测试由独立的 reviewer 编写，你看不到也不应猜测其内容。
- 不要为了实现方便而改动需求规格文件；规格有疑问时，在交付说明里列出，而不是自行解释。
- 交付时附一段不超过 5 行的说明：实现了什么、有哪些已知边界未处理。
```

`.claude/agents/blind-reviewer.md`：

```markdown
---
name: blind-reviewer
description: 盲测者。只读需求规格，不读实现代码，独立编写测试，并配合变异测试审计测试套件本身。
tools: Read, Edit, Write, Bash, Grep, Glob
---

你是盲测 reviewer。你只能阅读需求规格文档，禁止阅读实现源码后再写测试——先写测试，后看实现。

工作流程：
1. 只根据需求规格编写测试（正常路径、边界、错误输入）。
2. 测试写完后才允许运行实现并执行测试。
3. 运行变异测试（Python: `mutmut run && mutmut results`；JS/TS: `npx stryker run`）。
4. 对每个 survived mutant：要么补一条能杀死它的测试，要么论证该变种等价于原代码。
5. 输出三样东西：测试文件、mutation score、survived mutant 处置清单。
```

配套权限提示（写进仓库 README，不进 agent 文件）：blind-reviewer 的"盲"目前只能靠 prompt 约定 + 调用方不给源码路径来维持，属于概率机制；确定性兜底是变异测试——它不依赖 reviewer 自觉。这正是本期"对抗税"论点的实例。

## 作业（≤10 分钟，带外部判据）

**任务**：给你自己仓库里一份"agent 自写自测"的模块做一次审计。

1. 选一个实现和测试都由 agent 产出的模块（没有就现场让它产一个）。
2. 安装并运行变异测试：Python 用 `mutmut run`，JS/TS 用 `npx stryker run`。
3. 从 survived 列表里挑一个变种，手写一条能杀死它的测试。

**外部判据（全部满足才算完成）**：

- 判据一：`mutmut results`（或 Stryker 报告）中至少存在 1 个 survived mutant。若为 0，说明模块太小或太 trivial，换一个再跑。
- 判据二：补完测试后重跑变异测试，你挑选的那个变种状态从 survived 变为 killed。

不依赖自我报告：两个判据都是工具输出，跑不过就是没完成。
